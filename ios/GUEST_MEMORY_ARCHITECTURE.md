# Guest memory architecture for 16 KB hosts

## Phase 2C-1 access inventory

The inventory covers the runtime and static recompiler sources plus generated files under the ignored `.local/ios-port/generated/game/` directory. Generated game code was inspected in place and was not copied into tracked source.

The generated-code scan found `X86_MEM*` in 128 translation units, raw `X86_PTR` in 65 units, and atomic operations in 18 units. These counts overlap.

| Guest access category | Current mechanism | Required handling |
| --- | --- | --- |
| Recompiled scalar instructions | `X86_MEM8/16/32/64` dereference `base + guest_va`; emitted by `sdk/tools/recomp/codegen.cpp`; used throughout 128 generated translation units | Recompiler must emit checked reads and writes with width, direction, and full-span validation. |
| Recompiled raw pointers | `X86_PTR` in generated code; used in 65 generated units | Replace pointer escape with checked operations or pinned spans whose lifetime prevents decommit. |
| x87 and SIMD | x87 10-byte operands and 16-byte XMM loads/stores use raw `X86_PTR`; SIMD lane `memcpy` can also be local-only | Distinguish guest operands from local lane copies; validate complete 10/16-byte spans. |
| Atomic guest instructions | Recompiler emits atomic load, exchange, XADD, CMPXCHG, CMPXCHG8B, and bit operations through raw pointers; 18 generated units contain atomic operations | Add checked atomic operations with alignment, span, permission, and decommit synchronization. |
| REP/string instructions | `x86_rep_movs` and `x86_rep_stos` use direct `base + ESI/EDI`, `memmove`, `memcpy`, and `memset` | Validate full source and destination spans, overlap, direction flag, and fault/partial-progress behavior. |
| Kernel address helpers | `G<T>()`, `R16/R32/R64`, `W16/W32/W64`, and `HostPtr()` expose unchecked references, copies, or raw pointers from `g_base + va` | Replace raw references and pointers with checked scalar/span operations; direction and length must be explicit. |
| Boot and image loading | `boot.cpp` copies XBE headers and image sections directly through `g_base`; `XeLoadSection` uses `HostPtr()` | Use checked image writes and section permissions; validate zero-fill and raw/virtual lengths. |
| Kernel/HLE and OS I/O | `rtl.cpp` bulk operations; `files.cpp` passes guest buffers to file calls; `xnet.cpp` passes buffers to sockets; `xboxkrnl.cpp` contains atomic guest structure operations | Check the entire guest span before handing data to host APIs; copy or pin for the duration of asynchronous operations. |
| Threads and concurrent access | KPCR, ETHREAD, stack, and TLS initialization use `G/W`; guest work runs on host threads; audio and render workers can retain guest pointers | Use pinned views or copy-in/copy-out operations; serialize protection changes against active access. |
| Graphics | Vertex, texture, command, upload, and readback code uses `HostPtr()` and bulk copies; Vulkan and D3D12 paths access guest spans directly | Validate full row, texture, vertex, index, and command spans; pin or copy data for deferred GPU work. |
| Audio | Mixer and XDK sound paths use `HostPtr()`, typed helpers, and bulk copies, including asynchronous reads | Validate complete sample/block spans and lifetime across mixer callbacks. |
| Game/diagnostic hooks | Game/D3D hooks use `HostPtr()`, `G/R/W`, and C string or formatted-output routines; diagnostics export raw guest ranges | Replace with bounded guest APIs and explicit lengths. |

Changing `X86_MEM*` alone is insufficient. It misses `X86_PTR`, string helpers, kernel references and raw pointers, graphics/audio buffers, host I/O, and boot copies. The static recompiler must change and generated code must be regenerated outside tracked source. Host-side callers must also stop retaining unchecked guest pointers. `memcpy` in generated code is not automatically a guest access: several matches only pack local SIMD lanes.

The current memory manager stores commit bits at 4 KB granularity, but `IsCommitted()` is not a checked span operation. `NtProtectVirtualMemory` reports success without applying protection, `MmSetAddressProtect` is a no-op, and `MmQueryAddressProtect` always reports read/write. The Darwin backend therefore does not currently enforce guest permissions. A 16 KB host mapping cannot independently hardware-protect four 4 KB guest pages.

## Architecture choices

| Approach | Correctness | Complexity and speed | Memory and pointer compatibility | iOS fit |
| --- | --- | --- | --- | --- |
| A. Keep the linear guest mapping and add 4 KB software state | Correct only if every read, write, execute, and atomic access checks the complete range and decommit is synchronized with active users. Raw pointers bypass state. | Lower initial change; broad API conversion remains. Per-access page checks add cost; page-span pinning can amortize it. | Preserves sparse 4 GB VA and current backing layout. Existing direct pointers remain unsafe until every caller is converted. | Uses public file mapping and synchronization APIs; no JIT/private API needed. |
| B. Keep guest addresses logical and translate through a 4 KB page table to backing frames | Software page state is authoritative; one checked translation path can validate permissions, multi-page spans, and aliases. Correct once all access paths use that path. | Highest conversion effort: recompiler, kernel/HLE, I/O, GPU, and audio changes. Per-page translation costs more than direct pointer arithmetic; checked spans/pins can reduce repeated lookup. | Can retain sparse physical backing and map both physical aliases to the same frame. Raw host pointers must be removed or pinned through an explicit API. | Best fit for preserving guest semantics without relying on host sub-page protection. Uses public `mmap`/file backing; no executable-memory requirement. |
| C. Give each 4 KB guest page a separate 16 KB host page | Host protection can then represent each guest page independently. | Simpler protection semantics after translation, but every access still needs 4:1 address translation. | About 4x committed-page memory and address-space use; a 4 GB guest space expands to 16 GB before aliases. Existing direct pointers are incompatible. | 64-bit address reservation is plausible, but 4x physical cost is a poor mobile fit. |

Rounding host mappings to 16 KB is not an alternative: it changes neighboring guest-page state and permissions. Copying or pinning data does not remove the need for checked translation; it is an access API implementation technique.

## Selected direction and prototype boundary

Use **B** as the target architecture: guest VAs remain 32-bit logical values, each 4 KB PTE identifies a backing frame and logical permissions, and APIs validate the complete requested span before access. Physical and write-combined aliases refer to the same backing frames. Decommit/protection changes must synchronize with operations already using a page; APIs must not return unpinned pointers.

The Phase 2C-1 prototype is intentionally isolated from `sdk/runtime`. It demonstrates translation, page-level state, checked scalar/bulk/vector/atomic operations, alias coherence, and small boot-allocation shapes over a 16 KB host page. It does not convert the runtime, prove generated-code coverage, or establish game boot readiness. The existing runtime backend remains the fallback until full access mediation is implemented and audited.

## Prototype evidence and limits

The prototype has 64 logical 4 KB pages backed by a 256 KB temporary file and two `MAP_SHARED` aliases. Each four-page group maps to frames in reverse order, so logical addresses must pass through the page table. Initialization rejects hosts whose page size is not 16 KB. Checked reads, writes, bulk copy/fill, atomic increment, and execute checks validate the complete logical span before access; one mutex serializes operations against decommit and protection changes.

The test suite passed on macOS ARM64 and an ARM64 iOS Simulator with 16 KB host pages. It covers independent commit/decommit of all four guest pages within one host page, zero-filled recommit, per-page logical permissions, invalid and cross-boundary accesses, scalar and bulk operations, overlap-safe copy, a checked 16-byte span around an ARM NEON operation, alias coherence, concurrent increments, failed initialization, cleanup, and allocation-shaped probes.

These are wrapper-level logical permissions. Both host mappings remain read/write, so a raw pointer can bypass checks. `CheckExecute` is not connected to CPU instruction fetch. Permission metadata is shared by guest, physical, and write-combined aliases; alias-specific protection is not modeled. `FetchAdd32` is mutex-serialized only for callers using this API, and does not interoperate atomically with raw host accesses. Decommit clears page contents and state but retains the full 256 KB backing file and mappings, so it does not return individual 4 KB frames to the operating system. REP fault/partial-progress behavior, asynchronous I/O pinning, and all runtime/recompiler conversions remain unimplemented.

The allocation probes reproduce address alignment and access shapes; they do not call the Xbox runtime allocators or instantiate real KPCR/ETHREAD structures. The existing runtime memory-test target still rejects `AllocSystem(0x400, 64)`, an ETHREAD-sized allocation, and an unaligned `0x5000` image commit on the 16 KB host. Its 64 KB-aligned guarded stack probe succeeds. Therefore prototype semantics pass, but runtime boot-allocation readiness remains blocked.

## Phase 2C-2 production checkpoint

The production `sdk/runtime/kernel/memory` component now offers `CheckAccess`, `Read`, `Write`, `Copy`, `Move`, `Fill`, `FillPattern32`, `AtomicFetchAdd32`, `Protect`, and `IsInitialized`. Each checked operation validates the complete 32-bit span and every covered 4 KB guest page. One recursive mutex serializes checked access with commit, decommit, protection, and shutdown; checked operations copy data before releasing the lock. No checked API returns a pointer or holds a lock across a host callback. Future asynchronous host APIs must copy guest buffers or introduce a bounded pinned view with a lifetime that blocks decommit.

On Darwin, `Commit` opens the containing host page and zeroes only newly committed 4 KB guest pages. `Decommit` removes guest metadata independently; it protects and discards a host page only after its last guest page is removed. Empty host-page protection is applied before metadata changes, with rollback if a later protection call fails. If rollback itself fails, the memory manager becomes poisoned and rejects further checked access until shutdown. This rare OS failure path has no deterministic injection test yet. Both physical windows still alias the same file-backed RAM. Guest read/write/execute permissions are software metadata; raw host pointer access can bypass them. Non-Darwin memory mapping paths retain their existing host-page operations.

This is an intermediate software-state implementation over the existing linear 4 GB mapping, **not** the selected page-table/frame translation architecture B. `PhysicalFromVirtual` remains the legacy allocator translation, not a checked logical-to-frame translator. The production test invokes real allocators and checks KPCR/ETHREAD-sized fields, stack/TLS, image reservation, adjacent-page recommit, aliases, access rejection, atomic contention, and concurrent decommit/protection. It does not instantiate or start a guest thread.

`mem::Base()` returns null on Apple and `Boot()` stops with an error before any raw XBE or recompiled access. This prevents an unconverted caller from silently bypassing logical protection during startup. It also means Stages A and B are **partial**. Generated `X86_MEM*`, `X86_PTR`, REP/string operations, kernel `G<T>()`/`HostPtr()`, boot image loading, file/network I/O, graphics, audio, and asynchronous retained pointers remain unmediated. Stage C and startup-critical Stage D were therefore not entered. Precise x86 fault ordering, direction flag, partial progress, and guest exception delivery remain unimplemented. The full Phase 2C-1 access inventory above remains open.

The 4 KB sub-host-page change is Darwin-specific. Android/Linux hosts with 16 KB pages still use 4 KB `mprotect` ranges and have not been proven compatible. Software permissions are authoritative only for checked API users. Full runtime startup and game boot are unsafe until recompiler and host access paths are converted and reviewed.

## Phase 2C-3 checked recompiler checkpoint (historical)

The recompiler accepts `[xbe] checked_memory = true`; the default is `false`, preserving existing Android, Windows, and Linux emission. Checked mode uses `x86_mem_read<T>` and `x86_mem_write<T>` backed by production `mem::Read`/`mem::Write`. It is an explicit experiment, not enabled for the game image.

The whitelist is intentionally narrow: scalar MOV and MOVZX/MOVSX (8/16/32-bit destinations and 8/16-bit sources), 64-bit MMX MOVQ, non-locked memory ADD/SUB/INC, conditional branches, and RET. Every other instruction or operand shape is emitted as `x86_checked_trap`; locked instructions are always blocked. Checked RET saves local x86 flags before returning. Default emission is unchanged.

`ios/recompiler-fixtures/` builds a synthetic XBE and invokes the actual `xbe_recomp` executable. Generated C++ is compiled against production `sdk/runtime/kernel/memory.cpp` and kept under ignored `.local/ios-port/recompiler-fixtures-xcode/`. Tests cover valid and unaligned scalar and qword access, signed/unsigned loads, cross-4 KB guest pages on a 16 KB Darwin host, address overflow, uncommitted/no-access/read-only pages, fault PC/direction/status, no partial cross-page writes, ADD/SUB/INC results and flags, and safe blocking of unsupported instructions. No real game image or generated game source is part of the fixture.

The generated function catches `X86MemoryFault` and transfers its instruction PC, guest address, access direction, and `mem::AccessStatus` to `x86_memory_fault`. The production handler logs and aborts; generated read faults, denied writes, and blocked instructions are tested end-to-end in child processes. This provides deterministic stop behavior, not Xbox exception delivery. `mem::Read`/`mem::Write` validate the full span before copying, so a denied cross-page scalar write does not modify its committed prefix. The separate read and write steps of an unlocked RMW are not an atomic transaction. Guest page-fault priority, exception state, and recovery remain unimplemented.

SIMD/x87, atomics, and REP/string operations remain blocked in checked mode. The fixture demonstrates safe rejection for 16-byte MOVUPS, 10-byte FLD, implicit memory XCHG, locked XADD, and REP MOVSD. It does not claim instruction execution, atomic alignment/concurrency behavior, direction-flag semantics, overlap behavior, or REP partial progress. The memory manager's standalone 10-byte/16-byte span and atomic APIs remain separately tested.

At the Phase 2C-3 checkpoint, Apple kernel R8/R16/R32/R64 and W8/W16/W32/W64 used checked scalar APIs; KPCR/ETHREAD setup used checked whole-structure writes with allocation rollback; bounded C strings and counted ANSI strings used checked reads; and selected RTL operations used checked bulk APIs. That checkpoint's per-word `RtlFillMemoryUlong` loop could partially progress during concurrent decommit. Phase 2C-4 below replaces it with an atomic checked pattern fill. Darwin thread naming uses the Apple pthread signature. Non-Apple scalar, thread, string, and RTL paths retain their prior direct-memory behavior. `Boot()` still rejects the null Apple `mem::Base()` before raw access.

Remaining raw guest-pointer families include `kernel::G<T>()` and `HostPtr()`; launch-data and persisted-display copies in `boot.cpp`; other RTL string copy/conversion and interlocked exports; generated `X86_MEM*`/`X86_PTR` code outside the checked whitelist; file and network buffers; graphics, audio, and asynchronous I/O pointers; and runtime/game callers in `sdk/runtime/kernel`, `sdk/runtime/xdk`, `sdk/runtime/gpu`, `sdk/runtime/xdk/d3d8.cpp`, `sdk/runtime/xdk/dsound.cpp`, `sdk/runtime/xdk/xnet.cpp`, `src/d3d`, and `src/sound`. XBE preparation and section load/unload now use checked memory helpers, but the section helpers have not run as kernel exports. These remaining paths are not safe to enter on Darwin. The 16 static unsupported-instruction sites and their reachability procedure are recorded in [`PORT_STATUS.md`](PORT_STATUS.md#generated-x86-trap-sites); the existing generated game output also contains ordinary divide-error and `int3` calls to `x86_trap` outside that 16-site list.

**Startup remains NO-GO.** The checked fixture validates only the whitelist. The boot guard remains in place until XBE copies, raw host-pointer users, device buffers, and unsupported reachable instructions receive checked semantics and tests.

## Phase 2C-4 checked XBE preparation and startup audit

`xbe::Image::Parse` now bounds the header, section table, file ranges, image ranges, preload metadata, section overlap, entry point, kernel thunk terminator, certificate, and TLS ranges. `xbe::PrepareImage` checks the expected SHA-1 and entry point before reservation, then uses checked writes for the XBE header, preloaded section bytes, and reference counts; it zero-fills each virtual tail. A write or fill failure releases the prepared image and reports the operation, address, and access status. The injectable checked-write seam exercises a failure after partial preparation and confirms rollback. The real local Black Edition XBE parses and prepares through the same path without executing guest code.

`RtlFillMemoryUlong` now calls `mem::FillPattern32`. It rejects multiplication overflow, validates the full write span, then holds the memory lock across every dword store, preventing concurrent checked decommit from leaving a partial fill. Debug, optimized Release, and iOS Simulator tests cover cross-page success, overflow, denied cross-page writes with no partial progress, and a concurrent fill/decommit race that permits only a complete fill or a rejected fill. The same Release pass exposed and fixed an optimizer-sensitive overlapping copy between the two physical aliases: overlapping bytes now move in direction order through volatile accesses; non-overlapping copies retain `memcpy`.

`InitKernelData` uses checked scalar stores and a single checked ANSI descriptor/string write. `XeLoadSection` and `XeUnloadSection` resolve the section header against the parsed XBE section table and use checked fills, writes, and reference-count updates. Section load serializes against guest page changes, and a failed load clears its section bytes and decommits only pages it committed itself. A synthetic test injects a failed reference-count write after loading data, verifies rollback, and confirms a neighboring preloaded page survives on a shared 16 KB host page. These helpers compile and their checked memory paths are tested, but neither kernel initialization nor section exports were invoked in this phase.

The Apple `Boot()` null-base guard remains. The standalone loader test reaches real XBE preparation; application startup does not. Phase 2C-5 replaces the `boot.cpp` launch-data and persisted-display imports with bounded host reads and checked guest writes. Later guest exports and services still retain `G<T>()`/`HostPtr()` uses in kernel objects, RTL strings/interlocked operations, file and network I/O, graphics, audio, and asynchronous paths. The complete stage-by-stage ledger is in [`PORT_STATUS.md`](PORT_STATUS.md#startup-pointer-escape-ledger).

The real checked recompiler census still rejects over half of its generated instruction emissions. Selective additions to the existing checked-memory emitter are viable for staged startup work, but comprehensive game execution needs broader instruction and operand coverage, including stack/control flow, flags, implicit string operations, atomics, and x87/SIMD. This census is static output, not runtime frequency. The existing 16 original `x86_trap` sites remain a separate list from the new `x86_checked_trap` rejections.

**Controlled kernel initialization and game boot remain NO-GO.** Phase 2C-5 adds checked CMP semantics, but the next static entry blocker is `PUSH` at `0x002B393F`, followed by LEA, AND, and CALL blockers. The isolated synthetic preparation test stops before `InitKernelData`, dispatch setup, and thunk patching; no guest execution was used to establish runtime reachability. The Apple guard and all raw pointer families must remain gated until the full startup sequence and reachable host callers are checked and tested.

## Phase 2C-5 startup imports, CMP, and preparation boundary

Launch-data import now reads exactly 4096 bytes into a bounded host buffer, validates its contiguous allocation, copies the page and publishes its pointer with checked writes, and removes the source only after both writes succeed. Persisted display is imported only after launch-data import succeeds, preserving the existing quick-reboot pairing and avoiding stale frame imports on a cold start. The display importer checks its 28-byte header, marker, 8 MiB pixel limit, 1040-byte picture limit, overflow-safe total length, and exact file size. It writes pixels first and the 64-byte surface structure second, then publishes state and frees the prior allocation. Failure injection covers allocation, file-read, pixel/page writes, pointer/metadata writes, source preservation, neighboring bytes, and cleanup. A source-removal error after successful import is reported without discarding valid imported state.

Checked-mode CMP now computes CF, PF, AF, ZF, SF, and OF at the instruction width, sign-extends narrow immediates, preserves the destination, and uses checked memory reads with the original guest PC. AF is stored in `X86Context` and updated by ADD/SUB/INC as well. Generated fixtures use independent arithmetic references and cover branch behavior, unaligned and SIB addresses, carry/overflow/parity/half-carry, and uncommitted or denied reads. Unsupported instructions remain trapped.

The synthetic preparation checkpoint prepares a synthetic XBE, verifies its mapped entry, calls the production checked KPCR/ETHREAD initializer, validates the resulting fields, then releases its image, stack, and allocator ownership. It does not call `Boot()`, `StartThread`, `CallGuest`, or guest callbacks. The complete preparation gate remains blocked: `InitKernelData` starts a detached worker without a stop/join seam; `dispatch::Init` reads production generated-code globals; `MountDefaults` mutates process-global mappings and creates directories without reset; and the thunk-patching loop has no isolated synthetic fixture. Stage A import tests run independently rather than as one complete boot-preparation pipeline.

Raw-pointer callers remain in `sdk/runtime/kernel/kernel.h`, `files.cpp`, `objects.cpp`, `rtl.cpp`, and `xboxkrnl.cpp`; in `sdk/runtime/xdk/d3d8.cpp`, `dsound.cpp`, `hle.h`, `xapi.cpp`, `xnet.cpp`, and `crt_math.cpp`; in `sdk/runtime/gpu/render_thread.cpp`, `texture.cpp`, and `vertex.cpp`; and in `src/d3d/d3d8.cpp`, `src/d3d/render_thread.cpp`, `src/game/fe_mouse.cpp`, `game.cpp`, `game_font.cpp`, `hud_layout.cpp`, `options_menu.cpp`, `prompts.cpp`, `src/sound/buffers.cpp`, `device.cpp`, `mixer.cpp`, and `streams.cpp`. `sdk/runtime/gpu/d3d12.cpp` also contains raw accesses but is a Windows-only backend and is not compiled into the iOS target. `guest_strings.cpp` and `threads.cpp` contain raw `HostPtr()`/`G<T>()` fallbacks only off Apple; their Darwin string/thread paths use checked access. Remaining work includes bounded RTL copies and interlocked operations, object/critical-section and crypto fields, host file/socket buffers, graphics/audio buffers retained by deferred work, game/menu hook reads and writes, the x87 math-hook stack load, and default-mode generated `X86_MEM*`/`X86_PTR` operations. Checked-mode generated code only protects its supported instruction whitelist; it does not make these runtime/HLE callers safe.

The current detailed path table and static entry audit are in [`PORT_STATUS.md`](PORT_STATUS.md#startup-pointer-escape-ledger). The CMP at `0x002B3928` is now supported; the next emitted blockers are `PUSH` at `0x002B393F`, `LEA` at `0x002B3940`, `AND` at `0x002B3945`, and a direct guest `CALL` at `0x002B396A`. Static output does not establish runtime reachability. **Recommendation: NO-GO for kernel initialization or game execution; preserve the Apple `Boot()` guard.**

## Phase 2C-9 checked indirect CALL and runtime boundaries

This checkpoint adds checked-mode support for only the 32-bit absolute-memory `CALL [disp32]` operand form. The target dword is read through checked guest memory, then classified against the live dispatch table. Only mapped generated-function entries are admitted. Continuations, kernel and registered host thunks, null, uninitialized, unmapped, and unknown targets fail before the checked return-address write. Checked nested CALL/RET frame behavior and CALL/RET faults pass generated synthetic-XBE fixtures in Debug and Release. `dispatch::CallLease` prevents table reset while checked calls, legacy `x86_icall`, or continuations are running; legacy callback classes are still allowed and are not thereby checked. Reset remains a startup/rollback operation, outside guest execution.

Static inspection of the Black Edition XBE found `0x800000FF` at guest `0x003C9E68` (file offset `0x003BA148`), encoding import ordinal 255. The loader patches that import to kernel thunk `0xFE0003FC`, resolving to `PsCreateSystemThreadEx`. The writable guest image and guest/HLE stores mean a dynamic replacement is still possible; checked dispatch reads and classifies the current value on each call. The expected patched kernel thunk is rejected, and no game code ran. Later checked emissions include `TEST ECX,ECX`, same-function short JMP, `POP EBP`, `RET 0x18`, and caller `POP EDI`/`POP ESI`; these do not establish runtime reachability.

## Phase 2C-11 worker and IOSB lifetime boundaries

### Worker ownership and shutdown order

`WorkerLifecycle` owns host threads created for guest threads, DPC dispatch, and timer dispatch. Registration and timer/APC/DPC scheduling check the shared accepting state both before and under their queue locks. Shutdown disables acceptance, requests stop, wakes each owned wait (including guest delay and suspension waits), drains queued APC/DPC/timer work, closes the guest-dispatch gate, waits for active dispatch leases, and joins every owned worker before releasing worker-owned thread memory. Naturally exited workers are reaped on later registration, including registrations from managed workers; a joining state and condition variable prevent duplicate joins or shutdown races. Worker-creation failure rolls back registration. A joined manager can accept a later memory-runtime cycle. The NDK-compatible stop token stores callback lifetime state and waits for in-flight stop callbacks before their owner is destroyed.

`ClockWorker` remains a separate owner: `mem::Shutdown` stops and joins it before unmapping guest memory, even if its update callback previously failed. The callback dispatch path is `StartThread` → managed worker → `GuestDispatchLease` → legacy `CallGuest`; alertable APC delivery also acquires the dispatch lease in `RunApcs`. DPC dispatch holds a guest-dispatch lease around each callback. Timer expiry only queues DPC/APC work; it does not call guest code directly. `dispatch::CallLease` protects resolved dispatch entries while calls execute. Runtime rollback stops workers before `dispatch::Reset`, and memory shutdown stops and joins workers before page mutation and unmap.

Shutdown distinguishes an idle or suspended worker from one currently inside `CallGuest`. The former exits after its stop callback; the latter is not forcibly terminated and can block shutdown until guest instructions return. Legacy detached workers do not acquire this manager's gate, so this ordering is not a process-wide teardown guarantee yet.

The inventoried but excluded workers are:

- DirectSound's `StartHostThread` pump, which samples retained guest buffers and dispatches completion callbacks.
- The vertical-blank `StartHostThread`, which updates guest device state and can dispatch its guest callback.
- The XAPI controller poller, which periodically writes guest XPP state.
- The XNet socket pump, which copies received data and completion fields to retained guest VAs.
- The threaded GPU backend, which owns a detached worker and backend state with a bounded destructor wait.
- The Windows XAudio2 output thread, which repeatedly calls the DirectSound render function.

These categories require separate stop/join ownership and caller reset semantics before runtime teardown can claim global worker quiescence. Audio and vertical-blank paths remain specifically out of this phase as allowed by the stage scope.

Passing worker and IOSB tests establishes lifetime ordering only; it does not make callback targets, retained guest pointers, guest objects, or synchronization structures safe.

### Contiguous file IOSB page lease

`NtReadFile`/`NtWriteFile` now acquire `mem::ScopedPageLease` for the writable 8-byte IOSB before resetting completion state or touching the host file. Lease acquisition marks every covered 4 KB guest page and validates the full span under the guest-memory lock. It then releases that lock before file I/O. `Protect`, `Decommit`, `FreeVirtual`, and full-memory shutdown mark pages as mutating and wait for active leases without holding the global memory mutex; this prevents new leases while a mutation waits and avoids holding the memory lock across blocking I/O.

The export serializes operations using the file object's `io` mutex, then acquires the IOSB lease. Host read/write completes into or from bounded staging/checked guest buffers. Status and byte count are written together through one checked 8-byte memory write. Event and APC completion follow successful publication; the lease releases after signaling and also releases on early return, error, or stack unwinding. Memory shutdown stops managed workers, then waits on a whole-memory page mutation before releasing the mapping. The per-file lock is not held by memory mutators, and the page-lease mutex is released before entering checked memory operations, so the implemented lock order has no file-lock/global-memory-lock wait cycle in the tested path.

Export-level tests deterministically pause after host I/O while another thread attempts decommit or read-only protection. Both mutations wait until IOSB publication and completion signaling finish. Additional tests cover EOF, short reads, injected host read/write errors, repeated calls, invalid IOSB preflight, and shutdown during a paused export. The shutdown test verifies waiting and eventual publication, not interruption: no synchronous file-operation cancellation API exists, so a blocked host I/O call can delay shutdown. A failed or partial host write can still have changed the file, and a failed read can change the host cursor or guest data; those effects are not rolled back. Scatter/gather status blocks are intentionally unchanged and unleased.

**Guest execution remains NO-GO.** Worker ownership now covers the tested kernel worker families and contiguous IOSB publication is protected against concurrent guest-page mutation. Raw callback targets/arguments, object and critical-section fields, excluded detached workers, scatter/gather I/O, and other HLE raw accesses remain outside the safety boundary. See [`PORT_STATUS.md`](PORT_STATUS.md#phase-2c-11-worker-quiescence-and-iosb-lifetime) for test evidence and the Phase 2C-12 decision.
